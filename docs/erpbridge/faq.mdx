# Frequently asked questions

## MCP clients and transports

<details>
<summary>Which MCP clients can connect to the server?</summary>

The server supports two transports:

- **Streamable HTTP** for remote and web-based clients such as Postman at `http://localhost:8080/mcp/`
- **stdio** for local agents (Claude, Cursor) by running the binary with `--stdio`

See the [Connectivity and transport guide](./connectivity.mdx) for session setup.

</details>

<details>
<summary>Which MCP protocol version does the server negotiate?</summary>

The server speaks MCP 2025-03-26 and negotiates up to 2025-11-25 during the `initialize` handshake. Clients send the `initialize` request to `POST /mcp/`, then continue with session-managed requests.

</details>

<details>
<summary>How do I connect from Postman?</summary>

1. Send `POST http://localhost:8080/mcp/` with `Content-Type: application/json`
2. The `initialize` handshake creates a session
3. Use the returned session ID in `Mcp-Session-Id` for subsequent requests, then call `tools/list`

The [Postman setup](https://github.com/nmdra/ERPBridge/blob/main/docs/connectivity.md) in the repository shows the full flow.

</details>

## Configure ERPBridge and `bridgectl`

<details>
<summary>How do I configure the server?</summary>

Set the environment variables listed in the [Environment variables reference](./environment-variables.mdx). Export them in your shell, or set them in `docker-compose.yml`.

</details>

<details>
<summary>How do I configure the CLI?</summary>

The CLI reads `~/.bridgectl/config.yaml`. The file stores named contexts. Each context has `server`, `mcp-server`, `erp-base`, and an optional `api-token` value.

For HTTP authentication, the CLI uses the `--token` flag first, then
`BRIDGE_API_TOKEN`, and then the active context's `api-token`.

To switch contexts:

```bash title="Switch contexts"
bridgectl context list
bridgectl context set <name>
```

To override the address for one command:

```bash title="One-off override"
BRIDGE_MCP_SERVER=http://localhost:8080 bridgectl tool get
```

</details>

<details>
<summary>Why do `bridgectl cache` and `bridgectl log` fail with "connection refused"?</summary>

The default context points `server` at `http://localhost:8082`. Nothing listens there. Set `BRIDGE_SERVER=http://localhost:8080`, or edit the `server` value in `~/.bridgectl/config.yaml`.

</details>

<details>
<summary>How do I enable debug logging?</summary>

Set `LOG_LEVEL=debug` on the server. You can also set per-component levels, for example `LOG_LEVEL_MCP=debug`.

</details>

<details>
<summary>How do I run the server in JSON log mode?</summary>

Set `APP_ENV=production`.

</details>

<details>
<summary>Do I need Redis?</summary>

No. The cache uses a bounded in-memory LRU when `REDIS_URL` is empty. Set `CACHE_MEMORY_MAX_ENTRIES=0` to disable memory-cache storage. If `REDIS_URL` is set, Redis remains the selected backend even when it is unreachable; the server reports the backend error instead of silently using memory.

</details>

<details>
<summary>How does caching work and what is the default TTL?</summary>

The cache stores exact-match tool responses keyed by tool name, role, and request hash. By default responses do not expire (`ttl: 0`). Set a TTL in the server config to expire entries, or flush manually:

```bash title="Flush the cache"
bridgectl cache flush
```

See the [Exact Match Caching](./caching.mdx) guide.

</details>

<details>
<summary>When is a cached entry invalidated?</summary>

A tool schema can declare `flushOn` with a field path. When a tool call modifies that field, the server removes matching cache entries. To invalidate everything for a module, flush by module or use `bridgectl cache flush`.

</details>

<details>
<summary>How does the server protect ERP credentials?</summary>

Tool schemas reference credentials by name (`credentialRef`). The server resolves the reference from environment variables at call time, so schemas never contain raw secrets. Logs redact sensitive values: tokens, passwords, authorization headers, and PII, plus any value flagged with `secret` or `pii` tags. See the [redaction reference](./environment-variables.mdx).

</details>

## Notifications and system tools

<details>
<summary>What notifications does the server emit?</summary>

The server sends MCP notifications for long-running work:

- `notifications/progress` — progress on tool calls
- `notifications/alert` — alert-level events
- `notifications/message` — informational messages
- `notifications/tool_deleted` — when a tool disappears from the registry

</details>

<details>
<summary>What are the system tools?</summary>

Two built-in tools help you verify the bridge:

- `system.progress_test` — streams progress notifications
- `system.sensitive_log_test` — exercises log redaction

</details>

## Errors and exit codes

<details>
<summary>What do bridgectl exit codes mean?</summary>

- `0` success
- `1` general error
- `2` bad arguments
- `3` not found
- `4` authentication failure
- `5` conflict
- `6` timeout
- `7` precondition failed

</details>

<details>
<summary>How do I handle errors from the bridge in an agent?</summary>

Failures that an agent can act on return a machine-readable JSON body:

```json
{
  "error": "tool_execution_failed",
  "message": "The ERP service is unreachable",
  "suggestion": "Check that ERP_BASE_URL points at a running ERP",
  "code": 1
}
```

</details>

## Tools and schemas

<details>
<summary>Where do tool schemas come from?</summary>

The `schemas/` directory is not tracked by git. Generate the schemas from your ERP OpenAPI specification:

```bash title="Generate from OpenAPI"
bridgectl api register --name erp --url http://localhost:8081 --module erp --description "Mock ERP"
make generate-tools
bridgectl tool apply -f schemas/erp/
```

</details>

<details>
<summary>How do I update a tool?</summary>

Apply the new version with `bridgectl tool apply -f <file>`. The registry keeps multiple versions. MCP clients receive the latest stable version.

</details>

<details>
<summary>How do I hide a tool without deleting it?</summary>

Soft-delete it:

```bash title="Soft delete a tool"
bridgectl tool delete <name> <version>
```

The tool stays in the database. It no longer appears in `tools/list`.

</details>

<details>
<summary>How do I restore a soft-deleted tool?</summary>

Apply the schema again:

```bash title="Restore by re-applying"
bridgectl tool apply -f schemas/erp/<name>.json
```

</details>

<details>
<summary>How do I permanently remove a tool?</summary>

```bash title="Hard delete a tool"
bridgectl tool delete <name> <version> --hard
```

:::danger
A hard delete removes the tool from the database. You cannot restore it.
:::

</details>

<details>
<summary>How quickly does the server pick up tool changes?</summary>

Within 10 seconds. The reconciliation controller ticks every 10 seconds. A tool applied over the API is visible immediately.

</details>

## Authentication

<details>
<summary>How does the server authenticate ERP calls?</summary>

Tool schemas reference a credential by name (`credentialRef`). The server resolves the reference from environment variables at call time. Schemas never contain raw secrets.

The mock-erp service accepts:

- Token header: `token adm_key_001:adm_sec_stu901`
- Session cookie (`sid`)
- Basic auth: `admin:admin`

See [mock-erp in the repository](https://github.com/nmdra/ERPBridge/tree/main/mock-erp) for details.

</details>

## Upgrades

<details>
<summary>How do I upgrade ERPBridge?</summary>

1. Pull the latest changes: `git pull`
2. Rebuild the binaries: `make build`
3. Restart the containers: `docker compose up -d --build`

The SQLite registry keeps its data when the migration succeeds. If the server
cannot initialize the registry, inspect the startup error and correct the
database path or permissions before you restart the server.

</details>

## Troubleshooting

<details>
<summary>Tool calls return `internal server error`</summary>

Check the server logs:

```bash title="Server logs"
docker compose logs erpbridge-server
```

Common causes:

- The ERP service is unreachable. Make sure `ERP_BASE_URL` uses `http://mock-erp:8081` inside Docker.
- The tool endpoint path contains a secret pattern and was rejected.
- The selected Redis or in-memory cache backend is unavailable. Inspect the server logs and run `bridgectl cache stats`.

</details>
