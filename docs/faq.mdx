# Frequently asked questions

Use this page for orientation. Each answer links to the guide with the detailed configuration, protocol, or operational behavior.

## Understand ERPBridge

<details className="faq-item">
<summary>What is ERPBridge?</summary>

ERPBridge is middleware that connects existing ERP APIs to AI agents through the Model Context Protocol (MCP). It exposes ERP API operations as discoverable MCP tools without modifying the ERP codebase.

</details>

<details className="faq-item">
<summary>How does the integration work?</summary>

Register an ERP API with `bridgectl`, generate and validate MCP tool schemas, and apply those schemas to the server registry. The server exposes the active tools over streamable HTTP or stdio so MCP clients can discover and call them. See the [onboarding guide](./erpbridge/onboarding.mdx).

</details>

<details className="faq-item">
<summary>Do I have to modify my ERP?</summary>

No. ERPBridge sits at the API boundary and uses the REST APIs you already operate. It does not require ERP code changes, API rewrites, or database migrations. See [Connectivity](./erpbridge/connectivity.mdx) for upstream requirements.

</details>

<details className="faq-item">
<summary>What ERP systems can I connect?</summary>

Any ERP or service that exposes a REST API can be registered. On-premises systems, cloud suites, and custom services are supported as long as the server can reach the API and the required authentication can be configured. See [Authentication](./erpbridge/auth.mdx).

</details>

<details className="faq-item">
<summary>Which clients work with ERPBridge?</summary>

Any MCP-capable client can connect. Use stdio for local integrations, or streamable HTTP for remote and browser-capable clients. Claude, Cursor, Postman, and custom MCP clients are examples. See [Transports](./erpbridge/transports.mdx).

</details>

## Products and getting started

<details className="faq-item">
<summary>What is bridgectl?</summary>

`bridgectl` is the ERPBridge developer CLI. It manages API registrations, tool schemas, registry changes, cache, logs, contexts, API tokens, and shell completion. Start with the [bridgectl overview](./bridgectl/overview.mdx).

</details>

<details className="faq-item">
<summary>Does bridgectl include an agent skill?</summary>

Yes. ERPBridge ships the `bridgectl-ops` agent skill for onboarding, maintenance, authentication, observability, troubleshooting, and sanitized bug reports. Read the [skill usage guide](./bridgectl/skills.mdx) for its workflow and safety boundaries.

</details>

<details className="faq-item">
<summary>What does the ERPBridge SDK provide?</summary>

The `@erpbridge/sdk` package provides a typed MCP client, exact-name tool proxy, tool registry and direct-invoke wrappers, log and metrics access, health checks, and cache operations. See the [SDK overview](./sdk/overview.mdx) and [API reference](./sdk/api-reference.mdx).

</details>

<details className="faq-item">
<summary>Where should I start?</summary>

Follow the [server quickstart](./erpbridge/quickstart.mdx) to run the server and make a first MCP tool call. Use the [onboarding guide](./erpbridge/onboarding.mdx) when connecting your own ERP, or the [SDK quickstart](./sdk/quickstart.mdx) when embedding the client in a TypeScript application.

</details>

<details className="faq-item">
<summary>Can I try ERPBridge without a live ERP?</summary>

Yes. The repository includes a FastAPI `mock-erp` service and Docker Compose setup for local evaluation. The [quickstart](./erpbridge/quickstart.mdx) and [Docker deployment guide](./erpbridge/docker.mdx) use that environment.

</details>

## Security and operations

<details className="faq-item">
<summary>How is access secured?</summary>

Authenticated routes accept the admin credential or a scoped API token. Tokens can be limited to `mcp`, `metrics`, or `logs`, and token values are shown only once at creation. See [authentication](./erpbridge/auth.mdx) and the [API token guide](./erpbridge/tokens.mdx).

</details>

<details className="faq-item">
<summary>What observability is available?</summary>

The server exposes structured logs, recent-log and streaming endpoints, a health endpoint, and Prometheus metrics. The SDK and `bridgectl` provide typed or command-line access to those surfaces. See [REST API](./erpbridge/api.mdx) and [SDK Logs and metrics](./sdk/logs-metrics.mdx).

</details>

<details className="faq-item">
<summary>How does caching work?</summary>

Caching is opt-in per tool and supports Redis or a bounded in-memory fallback. Tool schemas can define TTL and `flushOn` invalidation rules. See [Exact Match Caching](./erpbridge/caching.mdx).

</details>

<details className="faq-item">
<summary>Where can I see what is shipped and planned?</summary>

Use the [Roadmap](./roadmap/overview.mdx) for the current status of the Server, bridgectl, and SDK. Shipped, in-flight, and future work have separate labels.

</details>

<details className="faq-item">
<summary>Where can I report a problem or request a feature?</summary>

Open an issue in the [ERPBridge GitHub repository](https://github.com/nmdra/ERPBridge/issues). Include the component, version, reproduction steps, relevant command or endpoint, and sanitized logs. For operational diagnosis, see [Skill Usage](./bridgectl/skills.mdx).

</details>
